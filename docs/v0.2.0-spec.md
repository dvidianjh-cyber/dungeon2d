# Dungeon2D v0.2.0 - Implementation Specification

## Context
This specification outlines the technical requirements for upgrading the Dungeon2D engine to version 0.2.0. Building upon the persistent UI, camera zooming[cite: 1, 2], and collision mechanics[cite: 4, 5] established in previous versions, this update focuses on Quality-of-Life (QoL) UI improvements and direct player interaction. The primary additions are a controls legend, interactive peer modals via mouse-picking, and a 1-on-1 private chat flyout.

## Requirements

* **Controls Legend:**
  * A floating UI element permanently anchored to the bottom-left corner of the viewport.
  * Must clearly document movement controls (WASD).
  * Must include a visual key explaining avatar colors (Green = Local Player, Blue = Peer Players)[cite: 8].
* **Peer Interaction Modals (Glassmorphism):**
  * **Hover State:** Hovering the mouse cursor over a remote peer's avatar must display a transient, glass-styled (`backdrop-filter: blur()`) tooltip showing basic peer information (e.g., player handle).
  * **Click State:** Clicking on a peer's avatar must lock the modal open as a permanent UI window. This window must display an interactive "Talk" action button.
* **Direct Chat Flyout:**
  * Clicking the "Talk" button must open a right-anchored sliding flyout pane.
  * The chat pane must facilitate a 1-on-1 private messaging interface strictly between the local player and the selected peer.

## Code Changes & Technical Implementation

* **`src/ui/UIController.js`**
  * Implement the bottom-left Controls Legend overlay using pure CSS flex/grid layouts, avoiding hard-coded pixel offsets[cite: 1, 6].
  * Create the DOM elements for the glass-style peer modal (managing visibility between hover/click states) and the right-side chat flyout.
  * Expose API methods to dynamically populate the chat pane, append new messages, and toggle flyout visibility.

* **`src/engine/RenderEngine.js` & Input Handling**
  * **Mouse-Picking Logic:** Implement a screen-to-world coordinate transformation function. This calculation must accurately reverse the fixed-center camera `ctx.translate()` and the global `zoomScale` applied to the Canvas[cite: 1, 2] to determine the cursor's true world position.
  * **Intersection Detection:** Check the transformed mouse coordinates against the cached 40x40 pixel AABB bounds[cite: 5] of remote peers to detect hover and click events. 
  * **Event Dispatching:** Dispatch successful interactions (e.g., `input:peer_hover`, `input:peer_click`) via the Event Bus to decouple the canvas from the UI[cite: 6].

* **`src/network/WebRTCEngine.js`**
  * **Targeted Messaging:** Extend the DataChannel payload schema to support a new `DIRECT_CHAT` event. Ensure logic is in place to route these messages only to the specific targeted peer rather than broadcasting to the entire room.
  * **Security:** All incoming chat payloads must be strictly sanitized using the existing `sanitizeString()` method[cite: 2] prior to rendering in the UI to prevent XSS vulnerabilities[cite: 6].

## Constraints & Edge Cases

* **Coordinate Mathematics:** Mouse-picking calculations must dynamically account for viewport resizing (`window.innerWidth`/`innerHeight`)[cite: 7], camera panning, and active zoom level.
* **UI Responsiveness:** The chat flyout, legend, and modals must remain responsive and fully functional on viewports down to 320px in width[cite: 1, 6].
* **Architecture:** Maintain strict separation of concerns. The Canvas rendering loop must not directly manipulate DOM UI elements; all state changes must be brokered through the custom Event Bus[cite: 6, 7].
* **Definition of Done:** Verify no placeholder comments remain, all new functions include JSDoc comments, and `CHANGELOG.md` is updated to reflect v0.2.0[cite: 1, 4, 6].
